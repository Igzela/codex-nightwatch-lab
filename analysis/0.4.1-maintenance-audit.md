## 2. Target Issue Audits & Resolutions

### Issue 1: Remove Trusted Event-Log 1 MB Lifetime Ceiling and O(n²) Validation
- **Root Cause:** In 0.4.0, `events.jsonl` was a single append-only file with a hardcoded `MAX_EVENT_BYTES = 1_000_000` check on every `_event_items()` and `load_state()`. Every state mutation called `load_state()`, which read and deserialized the entire history from disk, producing $O(n^2)$ read amplification over long runs.
- **Resolution:**
  - Implemented append-only segmented event storage under `<control-plane-dir>/events/`.
  - Added `events/manifest.json` tracking segment metadata (`seq_start`, `seq_end`, `event_count`, `byte_size`, `sha256`, `prev_sha256`).
  - Active segment defaults to bounded size (`DEFAULT_MAX_SEGMENT_BYTES = 500_000`). Once rotated, historical segments are sealed with SHA-256 digests chained to subsequent segments.
  - Implemented Pattern A backward compatibility: legacy unsegmented `events.jsonl` is recognized and preserved as immutable segment 0 without rewriting history.
  - Replaced full timeline parsing in `load_state()` with $O(1)$ frontier validation: validates manifest digest chain, directory listing match, `os.lstat()` size check on sealed segments, and reads only the tail record of the active segment.
  - Historical segment bodies are never read or deserialized during state loading or appending.
  - Uncommitted crashes before manifest updates are reconciled or truncated cleanly; corrupted sequences fail closed.
- **Verification Suites:** `nightwatch/tests/test_event_store.py` (12 tests covering lifetime limit removal, $O(1)$ frontier reads, rotation monotonicity, corruption/deletion fail-closed, legacy migration, restart recovery, and crash reconciliation).

### Issue 2: Hardened Persistent CODEX_HOME Inode Identity Recovery
- **Root Cause:** In 0.4.0, `ensure_codex_home` and `verify_codex_home` contained broad `except Exception: pass` blocks. If `codex_runtime_identity` or `codex_home_identity` were missing from state, it fell through to establishing a new directory or re-trusting whatever was on disk.
- **Resolution:**
  - Removed all `except Exception: pass` blocks from `storage.py`.
  - Hardened `models.validate_state`: strict shape checking requiring `[int, int]` (positive non-boolean integers) for both `codex_runtime_identity` and `codex_home_identity`. Both must be present together.
  - Handled all recovery cases strictly:
    - **Case A (Fresh initialization):** Safely creates trusted directories and immediately persists identities.
    - **Case B (Matching restart):** Validates that current disk inodes match recorded state; passes.
    - **Case C (Replaced inode):** Current disk inodes differ from recorded state; strictly fails closed with `StateIntegrityError`.
    - **Case D (Malformed identity):** `validate_state` rejects with `ValueError`, `load_state` fails closed with `StateIntegrityError`.
    - **Case E (Existing dir without recorded identity):** If persistent directories exist on disk but durable state lacks identities, fails closed unless explicit legacy migration flag `legacy_pre_identity_migration` is present.
  - Hardened `verify_codex_home()` to strictly fail closed without identities, never calling `ensure_codex_home` blindly.
- **Verification Suites:** `nightwatch/tests/test_trusted_home.py` (8 tests covering all cases A-E, malformed schemas, partial fields, and restart survival).

### Issue 3: Normalize Cross-Account Thread Capability Enum
- **Root Cause:** `models.cross_account_thread_mode_for_version()` accepted `"UNKNOWN"` as an override, but `validate_state` strictly rejected any state whose `cross_account_thread_mode` was not in `{"PROVEN", "UNSUPPORTED", "INCONCLUSIVE"}`.
- **Resolution:**
  - Removed `"UNKNOWN"` from accepted capability overrides in `models.py`. Valid modes are strictly normalized to `PROVEN`, `UNSUPPORTED`, or `INCONCLUSIVE`.
  - For Codex CLI 0.152.1, capability is recognized as `PROVEN`.
- **Verification Suite:** `nightwatch/tests/test_verification_dedup.py::AuthSanityAndCapabilityTests::test_cross_account_capability_mode_enum_rejects_unknown`.

### Issue 4: Stop NIGHTWATCH_CODEX_BIN From Implicitly Bypassing Auth Sanity
- **Root Cause:** Line 564 in `supervisor.py` had `if os.environ.get("NIGHTWATCH_SKIP_AUTH_CHECK") == "1" or os.environ.get("NIGHTWATCH_CODEX_BIN"): return True`, which allowed custom binaries to bypass preflight auth verification completely.
- **Resolution:**
  - Removed `or os.environ.get("NIGHTWATCH_CODEX_BIN")` from `_auth_sanity()`.
  - Auth check runs `[binary, "login", "status"]` for all binaries unless `NIGHTWATCH_SKIP_AUTH_CHECK=1` is explicitly specified.
- **Verification Suite:** `nightwatch/tests/test_verification_dedup.py::AuthSanityAndCapabilityTests::test_auth_check_runs_when_nightwatch_codex_bin_is_set` and `test_auth_check_bypassed_only_when_nightwatch_skip_auth_check_is_one`.

### Issue 5: Deduplicate Milestone Verification Commands Within One Verification Cycle
- **Root Cause:** In 0.4.0, `verify_milestones` ran the full set of frozen verification commands independently for every implemented milestone, and then ran the full set again for final checks. A plan with 8 milestones and 2 commands executed $(8 \times 2) + 2 = 18$ commands.
- **Resolution:**
  - Refactored `verify_milestones` to group eligible milestones (`status in {"working", "implemented"}` and `verification_profile == "default"`).
  - Runs the frozen policy commands once for all eligible milestones in that cycle, attaches evidence to all eligible milestones, and then runs one independent final check set.
  - Caps total command executions at exactly 2 sets per default-profile verification cycle, regardless of the number of milestones.
  - No caching across calls or repository mutations; subsequent calls re-verify independently.
- **Verification Suite:** `nightwatch/tests/test_verification_dedup.py::VerificationDedupTests` (6 tests with deterministic call counters asserting exact call counts and independence).

### Issue 6: Audit MAX_VERIFY_COMMANDS Limit Constant Drift
- **Root Cause:** `operations.py` defined `MAX_VERIFY_COMMANDS = 16`, while `tui.py` defined `MAX_VERIFY_COMMANDS = 20`. Furthermore, `RunSpec` did not enforce the limit during initialization.
- **Resolution:**
  - Standardized on authoritative limit `MAX_VERIFY_COMMANDS = 16`.
  - Enforced `len(commands) > MAX_VERIFY_COMMANDS` validation in `RunSpec.__post_init__`, raising `ValueError`.
  - Imported `MAX_VERIFY_COMMANDS` from `.operations` in `tui.py` and `cli.py`.
- **Verification Suite:** `nightwatch/tests/test_verification_dedup.py::VerifyLimitTests` (2 tests asserting 16 accepted, 17 rejected).

### Optional Cleanliness: Centralized Linux PID Identity Primitive
- Created `nightwatch/nightwatch/process_identity.py` containing `sys_platform_linux`, `pid_alive` (with Linux zombie process detection), `linux_process_identity`, and `process_identity_matches`.
- Replaced 3 duplicate copies across `supervisor.py`, `account_locks.py`, and `account_broker.py` with shared imports.
